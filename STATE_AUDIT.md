# State Data-Quality Audit

Living triage of per-jurisdiction WARN data quality. The table is **generated**,
not hand-maintained — regenerate it from a trusted environment:

```bash
# In-cluster, once the image containing the `audit` command is deployed
# (uses prod DATABASE_URL via secretKeyRef — no credentials leave the cluster):
warn-v2 audit --markdown
```

Paste the output between the GENERATED TABLE markers below, then hand-annotate the
**Source notes** section with Part-B findings (archive URLs, source caveats).

The audit logic lives in `warn_v2/scripts/audit.py` (`warn-v2 audit`). Everything in
the generated table is derived from the DB in a single pass; the **Source notes**
and **Backlog** sections are curated by hand from live-source inspection.

## Rubric

Each jurisdiction is scored on:

1. **Field completeness** — % non-null per model field the source could supply:
   `effective_date`, `layoff_count`, `closure_type`, `address`, `raw_notice_url`,
   `pdf_path`, `location_id`, company `naics_code`.
2. **PDF coverage** — for direct-PDF states (`raw_notice_url_is_pdf=True`): % of
   notices with a stored `pdf_path`, and whether the source URLs still resolve.
3. **Backfill / year completeness** — per-year notice counts; empty interior years
   are flagged; check whether an archive URL covers the gap.
4. **Geocoding accuracy** — NULL coords, coords outside the state bbox, and notices
   carrying a street address that should be street-level geocoded.

Plus the recurring failure modes (the `flags` column / `audit.py`): superseded
duplicates, estimated-vs-real `effective_date`, dead source links, HQ-vs-worksite
address, silent row-count drift, scraper failures, date/count sanity, low
enrichment.

## Legend

**Status**

| Symbol | Meaning |
|--------|---------|
| complete | No gap flags (a lone `has_superseded` note still counts complete). |
| gaps | One or more data-completeness flags (geo, pdf, dates, years, enrichment). |
| broken | Scraper failing, dead links, or silent row-count drift. |
| blocked / no data | Source unavailable, or no rows in DB. |

**Flags** (emitted by `warn-v2 audit`)

| Flag | Meaning | Remediation |
|------|---------|-------------|
| `low_geo` | <95% of notices geocoded | `backfill-geo` / `backfill-geo --rerun-address --state XX` |
| `out_of_state_coords` | geocoded point outside state bbox | fix geocode / verify worksite vs HQ address |
| `missing_pdf` | <90% PDF coverage on a PDF state | `download-pdfs --state XX` |
| `no_effective_date` | <50% have an effective_date | `backfill-effective-dates --state XX` |
| `mostly_estimated_dates` | >50% of effective_dates are the notice+60d estimate | source detail/PDF for real dates |
| `year_gaps` | empty interior year(s) | `backfill-historical --state XX` (extend `_SUPPORTED` if new) |
| `has_superseded` | superseded duplicates present | `mark-superseded --state XX --dry-run` then commit |
| `low_enrichment` | <50% of notices have an enriched company | `enrich --state XX` |
| `dead_links` | sampled `raw_notice_url`s 404 | fix scraper URL pattern (new code) |
| `row_drift` | last OK run below `expected_row_range` min | `/heal-scraper XX` (silent partial parse) |
| `scraper_*` | last run status not `ok` | `/heal-scraper XX` |
| `date_sanity` | future notice_date or effective<notice | inspect parser date handling |
| `count_outliers` | layoff_count <=0 or >50,000 | inspect parser count handling |
| `blocked` / `no_data` | known-blocked source or empty | re-check source access |

## Geocoding root cause (investigated 2026-06-11)

**`backfill-geo` is exhausted, and the low-geo states are not fixable by it.** The
nightly `backfill-geo` CronJob is healthy and runs (08:47 daily), but its last run
filled **0 of 517** remaining NULL-coord locations — those carry junk/unresolvable
addresses (e.g. PA "Various locations") with no ZIP/city centroid fallback.

Critically, the worst low-geo states' gap is **notices with no `Location` row at
all** — which `backfill-geo` (it operates on existing `Location` rows) can never
touch. Per-state breakdown of active notices lacking a location:

| State | Active | No location row | Root cause |
|-------|-------:|----------------:|-----------|
| DC | 141 | 141 | Source table has no city/ZIP/address column; all notices are in Washington, DC. |
| MN | 75 | 70 | Source has an "Account: City" column, but only the 2026 clean-table parser captures it; the historical 2025 wide/merged-cell format can't split "Name City Industry". |
| WV | 51 | 49 | Listing page is employer+date only; per-notice PDFs are stored but yield no parseable worksite address. |
| HI | 12 | 11 | Source page publishes no city/county/ZIP. |
| DE | 41 | 29 | Mostly no locality at source. |
| CO | 44 | 31 | A handful carry a bare street fragment on the notice (no city/ZIP). |

Cluster-wide there are only **87** active notices that have a `Notice.address` but no
`Location` row (PA 79, CO 5, CT 3), and **0 of the 87 contain a 5-digit ZIP** — the
PA 79 are descriptive multi-site strings ("Two locations in Breinigsville, PA…"),
not single geocodable points. So a "geocode the notice address" backfill would
recover only a few messy CO/CT rows — low value.

**Status of each (2026-06-11):**
- **DC — FIXED** (geo 0% → 100%). `storage._derive_location_city` defaults the
  *location* city to "Washington" (the source guarantees all are in-District). It
  derives the city for the Location only, so `notice_id` (hashed from the original
  row) is unchanged — existing rows fill in `location_id` on the next scrape via
  COALESCE; no re-key. Existing 141 backfilled.
- **MN — FIXED** (geo 4% → ~87%). `scrapers/mn_city.split_city_from_label` recovers
  the worksite city from the wide-format `Name City Industry` string (strip the DEED
  industry label, then longest trailing gazetteer match), wired through the same
  `_derive_location_city` hook. 65/70 backfilled; the 5 misses are out-of-state HQ
  cities the source lists (Bentonville, San Francisco, Omaha, …) or a truncated
  city — correctly left un-geocoded.
- **WV — FIXED via OCR** (geo 4% → 75%). **HI — FIXED via OCR** (geo 8% → 50%).
  Both states' per-notice PDFs are scanned images with no text layer, so
  `pdf_extract` now falls back to OCR (tesseract + poppler in the image) when
  `pdfplumber` yields no text. WARN letters address state officials, so naive
  extraction pins the recipient (WV → the WorkForce WV DOL at "Charleston, WV
  25305"; HI → the DLIR at "Honolulu, HI 96813"); `_choose_city_zip` excludes
  recipient-agency ZIPs + recipient-marker contexts (Rapid Response, Dislocated
  Worker, Director, Bldg/Room, PO Box), prefers worksite-cued matches, and takes
  the most-frequent in-state survivor — else leaves the notice un-geocoded rather
  than placing a false capital/HQ pin. Backfilled: WV 38/51, HI 6/12 to real
  worksites; the remainder are recipient-only letters with no parseable worksite.

## Source notes (hand-curated)

Findings the DB can't tell us — confirmed against the live sources.

- **Historical backfill routes** — per-state classification (published archive vs
  public-records request) lives in [docs/historical-sources.md](docs/historical-sources.md),
  verified 2026-06-12. Records-request drafts (18 states) in [docs/foia/](docs/foia/).
- **AK** — the stale-2016-link 404 issue is **fixed** (the scraper uses
  `jobs.alaska.gov/RR/notices/…`; verified 2026-06-11: stored `raw_notice_url`s
  and live source anchors all return 200, 49/64 notices have downloaded PDFs).
  AK's residual is a geo tail (66%): older notices without a PDF link + remote
  AK localities not in the city gazetteer — a hard tail, not a scraper bug.
  The interior **year gaps (2009, 2011, 2014) are real** — the cumulative source
  page lists zero notices for those years (verified 2026-06-12); no backfill needed.
- **CO** — Google Sheets export is cumulative since 2019; excluded from
  `backfill-historical` by design (re-ingest would duplicate).
- **CA / DC / AZ / DE** — current-year-only sources; historical years come from
  `backfill-historical`. CA archive = 11 PDFs + 1 XLSX (FY2014–2025).
- **GA** — `raw_notice_url` is a TCSG GravityView HTML entry page, not a PDF
  (`raw_notice_url_is_pdf=False`); enriched by `enrich-notices --state GA`. TCSG
  **rate-limits aggressively**: the enricher aborts after 3 consecutive timeouts, so
  a tail of notices stays location-less. **Hardened 2026-06-11** so this clears over
  nightly runs *without* hammering TCSG: commits every 5 (was 50) so each run durably
  banks what it fetched before the block; an unexpected error banks progress instead
  of crashing the Job. **2026-06-17**: `closure_type` reached 100%, which collapsed the
  old `closure_type IS NULL` ordering to deterministic newest-first — the same ~15-18
  notices were re-fetched every run (their gk-download is a Word/Excel doc, not a PDF,
  so they never left the candidate set) and starved the rest. Fixed with a per-notice
  `attachment_fetched_at` stamp (candidate query keys off it; one fetch per notice +
  timeout retries), and the gk-download attachment is now extracted for any type —
  the `.docx` is the WARN letter in full text (worksite address, dates, counts), the
  `.xlsx` is usually a job-title roster. `Company Address` on the entry page is often
  the corporate HQ, not the GA worksite → Census no-match / out-of-state coords, so the
  attachment's worksite is preferred when present. (Worksite city/zip extraction needs
  the 2-letter state form; letters that spell out "Georgia" still rely on the page's
  Zip Code/County — a `_choose_city_zip` full-state-name follow-up would close that.)
- **KY / MT** — county-only sources; geocoded via Tier-4 county centroid.
- **`inspect parser date handling`** appears widely — driven by the estimated-date
  heuristic (effective_date = notice_date + 60d). That's the expected WARN-Act
  fallback for many states, not necessarily a bug; treat as "real date unavailable
  at source" unless the source actually provides one.
- **Previously-flagged bugs now fixed** (confirmed in this table): MT/RI corrupt
  `notice_date` years (`225`/`204`) — fixed in place + `as_date` year-bounds guard;
  MT now 2015-2026, RI 2009-2026. GA scraper `fetch_failed` — now `ok`.
- **Blocked (not registered scrapers; appear in the audit only if legacy rows
  exist):** AR (confidential by law), NH (no public listing), OK
  (Salesforce/Aura auth wall), TN (scraper built; tn.gov blocks container IPs),
  WY (no public data). Re-verify each blocker periodically.

## Optional enhancement

`Location` now has a `geocode_source` column (`census`/`zip`/`city`/`county`), so
the audit could read the stored tier directly instead of inferring geo accuracy
from address availability + coord presence. Wiring the audit to use it would make
geo-accuracy reporting exact and re-runnable.
